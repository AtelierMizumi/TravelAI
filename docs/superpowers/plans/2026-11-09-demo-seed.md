# Demo Seed (#44) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline, chosen by owner). Steps use checkbox syntax.

**Goal:** Idempotent loader that fills the production DB, through the real backend API, with enough demo data to walk the whole app from A to Z.

**Architecture:** `data/seed/*.json` (content) + `scripts/seed/seed_demo.py` (stdlib-only HTTP client, ordered flows, idempotent by lookup) + `scripts/seed.sh` (backup, admin bootstrap, run). Images are local copies served by Caddy at `/media/`.

**Tech Stack:** Python 3 stdlib, bash, Caddy, existing Spring Boot API.

**Spec:** `docs/superpowers/specs/2026-11-09-demo-data-cicd-design.md` (main repo) section 3.

## Global Constraints
- Load only through the public API (`PUBLIC_ORIGIN` or `--base-url`); the only SQL allowed is promoting the first admin.
- Passwords come from env (`SEED_ADMIN_PASSWORD`, `SEED_USER_PASSWORD`); never in files, logs or chat.
- Demo accounts use `@demo.travelai.test`; no real person's name, photo or contact.
- Every image has an `ATTRIBUTION.md` row (title, author, license, source URL); only CC0/PD/CC BY/CC BY-SA.
- `pg_dump` backup is mandatory before any write; never `down -v`.
- Re-running must create nothing new; `--dry-run` writes nothing.
- No commit/push beyond the integration branch; no `main`.

## Review Focus
- Second run duplicates rows (places/tours/hotels/offers/posts) (Task 2/3).
- A failed step midway leaves a half-seeded DB that a re-run must complete, not duplicate (Task 2/3).
- Passwords or tokens printed in output (Task 3).
- Image served with wrong type/404 through the tunnel (Task 4).
