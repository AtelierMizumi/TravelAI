# Ngoc TravelAI 2.0 Integration, Design Spec

Date: 2026-11-08. Owner: Tran Minh Thuan (Tech Lead). Status: awaiting review.

## 1. Goal

Produce a running integrated build (PostgreSQL, Spring Boot backend, AI service, Expo app) on the owner's machine so the owner can test **web (desktop browser), Android (physical device)** and report defects. iOS is out of scope (no Mac, no Apple account).

Done when, on each in-scope platform: login, tour search, tour booking with simulated payment, and landmark/food image recognition work end to end, and a defect list exists for anything that does not.

## 2. Findings that shape the design

- Source: `github.com/ngoctapcodee/travel-ai-system` (public), 2 squashed commits, head `5799682`. No shared git history with this repo, so a git merge is impossible. Integration is a **snapshot import**.
- It is a rewrite ("TravelAI 2.0"), not an extension: backend package `com.travelai.backend` (ours `com.travelai.core`), Java 25 (ours 17), 29 tables, one Expo SDK 58 / RN 0.88 app for web+Android+iOS replacing `client/`.
- No desktop target exists in either repo.
- Local toolchain: Java 21, Docker, adb, Android SDK present; no `mvn` (use `mvnw`), no `psql`, no emulator binary on PATH.
- The Google service-account key is gitignored upstream; this repo's `.gitignore` does not yet cover it.

## 3. Decisions (approved by owner)

1. **Strategy: baseline first, then import.**
   - Phase A: run Ngoc's repo unmodified in a scratch directory outside this repo to establish a baseline (what works/breaks before any integration).
   - Phase B: branch `integration/ngoc-2.0` from `main`; import the snapshot keeping upstream paths (`apps/mobile`, `backend/`, `ai-service/` reference only). No package renames, so future re-syncs stay cheap. Existing `client/` and `services/core` stay untouched until the team retires them.
   - Keep this repo's DevOps (docker-compose, CI, governance hooks); adapt compose to build from the imported backend and app.
2. **AI service:** `services/ai` (owner's WBS 1.3.x) remains authoritative. Port only endpoints the new app calls that it lacks (food recognition, Gemini) after reading upstream `ai-service/ai/main.py`.
3. **Desktop = Expo Web in a desktop browser.** Electron/Tauri is out of scope unless the course brief explicitly demands it.
4. **Mobile = physical Android** via USB + `adb reverse` + `expo run:android` (or Expo Go on Wi-Fi). iOS excluded.
5. **Database:** fresh PostgreSQL 16 in Docker seeded from upstream `data.sql`/`db`; no existing database touched. Upstream message-encryption key is generated fresh for this dev DB only.
6. **Java:** try JDK 21 first (upstream says tests passed on 21); install JDK 25 via `paru` only if the build requires it.

## 4. Secrets handling

- Add `*service-account*.json` and the key directory to `.gitignore` **before** the key is placed anywhere in the repo tree.
- Key lives at `services/ai/` (gitignored), is mounted into the container as a read-only volume, never baked into an image, never committed, never echoed in logs or chat.
- The key was shared via chat and Discord; treat as exposed and rotate after the demo.
- Run `scripts/governance-check.sh` before any commit; no `*.pdf/docx/xlsx/csv` in the diff.

## 5. Governance constraints

- Cross-scope work (Ngoc's frontend, Duc's backend areas) is done at the owner's explicit request; commits use the owner's git identity, flagged cross-scope in the PR, no assistant trailers.
- No commit/push unless the owner asks; never touch `main` directly; PR targets `main` for owner review.
- Conventional Commits with issue ID. Sprint 5 (2026-11-02..2026-11-15) is current; report status, do not adjust dates.

## 6. Verification plan (outline; detailed steps go in the implementation plan)

| Layer | Evidence |
| --- | --- |
| Baseline (Phase A) | upstream `npm run check`, backend tests via `mvnw`, AI tests; record pass/fail |
| Integration | `docker compose up` healthy; backend health endpoint; AI health + one image recognition call |
| Web | Expo Web in browser: login, tour search, booking+payment, image recognition (Playwright smoke) |
| Android | Real device: same journey; screenshots/logcat captured for defects |
| Defects | Single list: platform, steps, expected/actual, owner (Ngoc/Duc/Thuan) |

## 7. Out of scope

iOS builds, Electron/Tauri, production deployment, schema migration of any existing database, retiring `client/` and `services/core`.

## 8. Risks

- Java 25 vs 21 mismatch; Expo SDK 58 compatibility with Expo Go (fallback: dev build via `expo run:android`).
- AI mock vs real Vision mode: real mode requires the key and network; baseline runs in whichever mode upstream defaults to, then switched explicitly.
- Upstream tests were run on Ngoc's machine only; a green baseline is not assumed.

## 9. Amendments made during execution (2026-11-08)

- **AI service (supersedes decision 2):** upstream `ai-service/` is imported and used by profile `v2`; `services/ai` is untouched. Reason: the app calls `POST /detect` (about 1,000 lines: Vision, Wikipedia, fallback), while `services/ai` serves `/api/v1/vision/recognize` with a different schema; porting was not proportionate.
- **Branch base:** `integration/ngoc-2.0` is based on `feat/wbs-1.8.2-docker-compose-integration`, not `main`, because the healthchecked compose, AI Dockerfile and CI exist only there.
- **Android target:** Waydroid (Android 13 x86_64) with Expo Go, not a physical phone; camera paths are untested.
- **Containers** run as the host uid/gid (default 1000) so 0600 secret files stay readable; ports bind to 127.0.0.1 by default.
